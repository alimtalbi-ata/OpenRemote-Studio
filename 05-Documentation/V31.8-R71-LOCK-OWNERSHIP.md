# OpenRemote Studio V31.8-R71 — Resume lock ownership qualification

**Author:** Abdelhalim Talbi  
**Date:** 2026-10-23  
**Scope:** SFTP verified resume; local lock ownership; Windows packaging unchanged.

## Defect and risk
R70 acquires a lock using `O_EXCL`, but later unconditionally deletes the lock path. If another process removes/replaces that path during an SFTP transfer, R70 can publish the downloaded data without owning the lock and can delete the replacement owner's lock. This is a concurrency and integrity defect.

## R71 implementation
- Capture the exclusively created lock's POSIX identity (`st_dev`, `st_ino`) and write a random 32-byte owner marker. On Windows, use the marker rather than relying on mismatched file identity metadata between `fstat` and path stat.
- Check the lock is a regular file and contains the same marker immediately before publication; additionally verify device/inode on POSIX.
- On cleanup, do not knowingly unlink a lock whose identity differs from the original. Preserve staged bytes when publication is rejected.
- Retain `O_EXCL`, `O_NOFOLLOW` where supported, and fail closed when ownership is lost.
- No automatic stale-lock deletion. No production secrets. No destructive deployment.

## Architecture and dataflow
```text
SSH/SFTP remote file
       |
       v
resume lock (O_EXCL) -> capture file identity
       |
       v
verify partial prefix -> download remaining bytes -> fsync
       |
       v
verify remote metadata + cancellation
       |
       v
check lock identity -> if lost: refuse publication; preserve target/partial
       |
       v
os.replace(staging, target) -> cleanup lock only if still owned
```

## Known limitations
This is a best-effort ownership check, not an atomic compare-and-unlink operation. Another process can still race after `lstat` or before `unlink`. Full OS-level locking and atomic destination compare-and-swap remain future work. Do not present these unit tests as a complete concurrency proof.

## Release policy
Draft PR only; preserve `main`. A Windows installer/portable qualifies R71 only when built by Windows CI from the exact R71 HEAD. Baseline R70 executables cannot be relabeled as R71.

## Windows CI correction during R71
The first cumulative Windows run (#39927795417) failed in the historical `test_resume_after_interruption`: Windows returned inconsistent lock metadata between descriptor and path. The first implementation used `st_ctime_ns` as part of lock identity and incorrectly rejected a valid transfer. The corrected implementation uses a random lock owner marker plus POSIX device/inode when available. The new same-inode tampering test guards this change. CI must be rerun and rechecked on the new SHA before declaring a Windows release qualified.
