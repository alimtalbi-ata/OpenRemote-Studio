# V31.8 R89 — Diagnostics SSH expurgés et reprise contrôlée

**Auteur : Abdelhalim Talbi** · **Date : 24 octobre 2026** · **État : branche de développement, CI à vérifier au SHA exact**

## Problème métier P1
Le panneau Qt affichait le même message « échec SSH » pour une empreinte d'hôte refusée, une clé privée rejetée ou une panne générique. L'opérateur pouvait retenter manuellement, mais sans indication sûre sur le type de correction. Les textes d'exception Paramiko peuvent contenir des hôtes, chemins locaux ou identifiants et ne doivent jamais être exposés.

## Implémentation
- `Application/tunnel_controller.py` classe **par type** `BadHostKeyException` → `host_key`, `AuthenticationException` → `authentication`, autres → `generic`. Pas d'analyse du texte de l'exception.
- `TunnelSnapshot.failure_code` ne transporte qu'une valeur fixe ; valeur par défaut `none`. Aucun nom d'hôte, utilisateur, clé ou jeton.
- `Application/ssh_tunnel_qt.py` affiche une action sûre : vérifier `known_hosts` **hors bande** ou vérifier la clé privée. Les erreurs inconnues restent génériques.
- Les contrôles de nettoyage R88 restent prioritaires : aucune nouvelle tentative tant que le listener ou les canaux ne sont pas libérés. Un nouveau contrôleur et un nouveau consentement sont obligatoires. **Jamais de TOFU, jamais de reconnexion automatique.**

## Scénario OpenSSH réel (CI isolée uniquement)
1. Lancer un serveur OpenSSH Docker éphémère sur `127.0.0.1:2222`, avec clé cliente Ed25519 autorisée.
2. Fournir un fichier `known_hosts` volontairement faux. Attendre `failed/host_key`, vérifier l'absence de listener.
3. Récupérer la clé publique du serveur **par le plan de contrôle du laboratoire**, remplacer explicitement `known_hosts` et créer un **nouveau** contrôleur.
4. Vérifier le forwarding réel (bannière `SSH-2.0-`), puis arrêter et drainer les ressources.
5. Utiliser une clé cliente non autorisée : attendre `failed/authentication`, vérifier qu'aucun chemin sensible n'est exposé.

Le script `Application/tests/live_ssh_tunnel_retry_r89.py` n'accepte que le loopback du laboratoire, ne modifie aucun serveur de production et ne sauvegarde aucune clé dans les artefacts. Ce test valide la reprise **backend** ; il ne simule pas un clic humain dans Qt.

## Qualification et limites
- `test_tunnel_failure_classification_r89.py` : trois tests de classification (Paramiko requis pour deux).
- `test_tunnel_failure_guidance_qt_r89.py` : quatre tests de libellés et de blocage de reprise (PySide6 requis).
- CI OpenSSH et CI Windows native/cumulative ajoutées : **résultats non présumés** avant lecture des runs.
- Le serveur de production, la capture de trafic blackhole, l'interface opérateur physique et les rotations de secrets Vault ne sont pas qualifiés par R89.
- R88 reste la dernière version ayant un ZIP cumulatif attesté ; ne pas annoncer d'installateur R89 tant que la CI cumulative n'a pas livré son artefact vérifié.
