# OpenRemote Studio V31.8 — R124 : interruption coopérative du SFTP actif

**Auteur : Abdelhalim Talbi.** **Date : 26 octobre 2026.** Statut : correctif proposé sur branche dédiée ; qualification finale à lire dans les runs GitHub du SHA de tête.

## Défaut observé

R123 distinguait correctement `cancelled` de `failed` et ne libérait la file qu'après le signal terminal. Mais `SftpJob.cancel()` ne faisait que poser un `Event`. Si Paramiko était bloqué dans un appel SFTP réseau, aucun callback de progression ne pouvait lire cet Event ; le worker et la file active pouvaient rester occupés jusqu'au retour du socket.

## Correction

- Le worker conserve une référence protégée par verrou au client SSH actif.
- `cancel()` pose d'abord l'Event, copie la référence sous verrou, puis tente de fermer le client hors du verrou. La fermeture du transport est un mécanisme d'interruption coopératif pour un appel SFTP déjà bloqué ; aucun thread n'est tué de force.
- Après le retour de la fonction de connexion, le worker vérifie la demande d'annulation avant d'ouvrir un canal SFTP. Cela couvre la course où l'annulation arrive pendant la connexion.
- Une erreur de transport consécutive à une demande d'annulation est classée `cancelled`; une erreur non sollicitée conserve l'état `failed`.
- Le nettoyage du contexte SFTP et la fermeture finale restent exécutés avant le signal terminal. Les erreurs de fermeture ne remplacent pas le résultat terminal et ne sont pas journalisées.

Le verrou ne reste pas détenu pendant `client.close()`, afin de ne pas bloquer l'enregistrement/le drainage du worker derrière une opération de fermeture.

## Tests et gates

`Application/tests/test_sftp_cancel_interrupt_r124.py` vérifie :
1. fermeture du client actif qui libère un appel de liste volontairement bloqué ;
2. classification `cancelled` d'une erreur de socket provoquée par la fermeture, même si `close()` lève une exception ;
3. conservation de `failed` pour une panne transport non sollicitée ;
4. absence d'ouverture d'un canal SFTP quand l'annulation arrive pendant `connect_fn()`.

Les fixtures sont déterministes et ne contactent aucun service externe. Le test nécessite PySide6 ; les lanes Windows native, OpenSSH/SFTP et cumulative doivent l'exécuter sans skip. La gate OpenSSH continue aussi d'exécuter ses vrais scénarios SSH/SFTP sur le serveur jetable. Cela qualifie la non-régression du transport et des transferts, mais **ne constitue pas à elle seule une preuve qu'un appel réseau arbitraire à tout serveur sera interrompu instantanément**.

## Limites de sécurité et d'exploitation

La fermeture du client est « best effort ». Si le blocage se trouve dans `connect_fn()` avant qu'un client ne soit retourné, le worker ne possède encore aucun objet à fermer ; cette phase reste tributaire du retour ou des délais de connexion déjà configurés. Une opération distante peut avoir terminé juste avant que l'annulation arrive ; le statut local ne remplace pas la vérification de l'état distant. Ne jamais utiliser ce mécanisme comme rollback de fichier distant. Aucun identifiant, contenu de clé ou secret n'est journalisé par ce correctif.

Pas de changement UI ; **aucune capture R124 n'est revendiquée**. La recette sur serveur d'entreprise, l'annulation en production et les délais absolus toutes phases confondues restent **UNVERIFIED**. Auteur : Abdelhalim Talbi.
