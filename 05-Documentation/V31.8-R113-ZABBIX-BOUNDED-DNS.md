# OpenRemote Studio V31.8 — R113 : attente DNS bornée par l'échéance Zabbix

Auteur : **Abdelhalim Talbi**. État au dépôt du code : implementation et tests ajoutés ; la qualification des workflows Windows, OpenSSH et cumulative doit être vérifiée au HEAD exact avant toute déclaration de release.

## Lacune P1 corrigée

R112 applique une échéance monotone à la transaction HTTPS, mais `socket.getaddrinfo()` est appelé dans le thread de connexion. Le résolveur système peut bloquer dans une API native que Python ne peut pas interrompre de façon portable ; le thread appelant pouvait alors dépasser le délai, même si le watchdog de socket était armé.

## Comportement R113

- `Application/zabbix_readonly.py` confie maintenant la résolution d'hôte à `_DeadlineDNSResolver`, avant la création du socket TCP.
- Le résolveur utilise **deux workers daemon au maximum** et une file d'attente globale de **deux demandes**. Il ne crée pas un thread par requête ; une panne DNS ne peut donc pas produire un nombre illimité de threads résolveurs.
- Le thread demandeur attend uniquement jusqu'à l'échéance monotone existante. File pleine, résultat absent ou deadline expirée donnent un timeout neutre ; aucun détail brut du résolveur n'est affiché.
- Une tâche restée dans la file au-delà de sa propre échéance est abandonnée avant l'appel suivant à `getaddrinfo`.
- La résolution terminée alimente la création TCP déjà protégée par le watchdog R112. TLS, validation de certificat et du nom d'hôte, refus des redirections, plafond de réponse de 1 Mio et méthodes JSON-RPC en lecture seule restent inchangés.
- Le pool est fixe et la file bornée. Une résolution OS bloquée peut néanmoins continuer dans un worker daemon ; si les deux workers restent bloqués, les nouvelles demandes sont refusées ou expirent plutôt que de créer davantage de threads. Le pool se remet à traiter des demandes lorsque l'OS libère un worker.

## Tests R113

`Application/tests/test_zabbix_dns_deadline_r113.py` contient six tests :
1. une deadline déjà expirée ne démarre aucun worker ;
2. une réponse normale conserve la forme `getaddrinfo` ;
3. le chemin de connexion TCP utilise le pool et un socket loopback réel ;
4. un résolveur injecté qui ne répond pas ne retient pas l'appelant au-delà de la deadline ;
5. une tâche DNS expirée en attente ne démarre pas après libération du worker ;
6. le nombre de workers et la taille de la file restent bornés sous saturation.

Ces tests utilisent des résolveurs injectés, des primitives de synchronisation et une socket locale. Ils ne contactent ni DNS public ni serveur Zabbix, n'utilisent aucun jeton réel et ne valident pas les permissions d'une instance de supervision.

## Qualification et limites

Les gates Windows native, OpenSSH live et cumulative doivent exécuter le test R113 et compiler le module. Les résultats ne seront revendiqués qu'après lecture des trois workflows associés au commit exact. Aucun binaire, ZIP cumulatif ou hash de release R113 n'est attesté par cette note seule.

Le résolveur OS n'est toujours pas « tué » par Python : R113 borne l'attente du thread appelant et limite les opérations DNS abandonnées à un petit pool fixe. La vraie recette d'une instance Zabbix HTTPS avec un rôle en lecture seule effectif, le jeton de laboratoire, le filtrage/rate limit en charge et l'acceptation opérateur restent **UNVERIFIED**.
