# OpenRemote Studio V31.8 — R98 : évolution des services WinRM (lecture seule)

Auteur : **Abdelhalim Talbi** — 24 octobre 2026.

## Problème opérationnel

R97 permet une lecture exacte de l'inventaire des 128 premiers services, mais deux
lectures successives ne signalaient pas les changements d'état ou de démarrage.
L'opérateur devait comparer manuellement les résultats. R98 ajoute une comparaison
**locale** entre deux lectures explicitement déclenchées sur la même origine et
le même compte, sans nouvelle requête réseau pour le calcul ou le filtrage.

## Fonctionnement et invariants

- **Outils → Services Windows WinRM (lecture seule)** : cinquième colonne
  « Évolution » ; exemple `Running → Stopped; Auto → Manual`.
- La première lecture réussie crée la référence volatile. La deuxième calcule
  les transitions d'état et de mode de démarrage des services communs.
- Les ajouts/disparitions ne sont comptabilisés que si **les deux** inventaires
  sont complets. Si l'un est tronqué à 128, aucune disparition/ajout n'est
  inféré; le panneau indique explicitement « non évalués ».
- La modification de l'origine, du compte, du consentement, le masquage ou la
  fermeture du panneau efface la référence. Les réponses tardives sont ignorées
  par la barrière de génération existante.
- Le filtrage local n'émet aucun POST WinRM. Pas d'export, de journalisation de
  données distantes ni de persistance de la référence.
- Les champs des services sont validés et bornés; une réponse incohérente
  produit uniquement le code fixe `winrm_invalid_response`.
- L'authentification reste temporaire, HTTPS avec validation TLS, lecture
  seule, hors ligne par défaut et consentement explicite.

## Architecture

```text
Opérateur (Qt) ──consentement explicite──> WinRMServicesReadOnly
  │                                        │
  │                                        └─ HTTPS WinRM (script CIM constant)
  │                                                   │
  ├─ référence volatile (128 max) <────── réponse normalisée
  │
  └─ winrm_service_drift.compare_service_snapshots
        ├─ services communs : état + mode de démarrage
        ├─ inventaires complets : ajouts/disparitions
        └─ inventaire tronqué : ajouts/disparitions non évalués
                      │
                      └─ Qt : colonne Évolution + résumé
```

## Preuves et limites

- `Application/tests/test_winrm_service_drift_r98.py` : **8/8 PASS local POSIX**
  sur le module pur R98 (pas de transport WinRM).
- `Application/tests/test_winrm_service_drift_qt_r98.py` : 4 scénarios
  d'interface synthétiques ajoutés; résultats Windows CI à vérifier au SHA.
- Tests R95/R97 et suites SSH/Windows doivent rester verts au HEAD.
- **Non qualifié** : serveur Windows Server WinRM HTTPS réel, secrets du coffre
  par référence, recette humaine Windows physique, perte WAN réelle.
- Capture R98 de la colonne « Évolution » : **absente tant que le workflow
  Windows ne produit pas de capture réelle**; aucune simulation n'est une preuve.
- Installateur/portable/ZIP R98 : **non revendiqués avant CI cumulative et
  vérification SHA-256 de l'artefact exact**.

## Prochain cas d'usage

R99 : intégrer une référence de coffre au parcours WinRM sans secret dans
les profils/exports; qualifier un serveur Windows isolé avec compte de lecture
minimal. Ne pas fusionner automatiquement `main`.
