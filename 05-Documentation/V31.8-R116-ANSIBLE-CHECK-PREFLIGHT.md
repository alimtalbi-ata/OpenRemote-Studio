## 1. Objectif et état honnête

R116 apporte un premier parcours Ansible utilisable dans OpenRemote Studio, au lieu d'un simple lien vers un outil externe. L'onglet **Outils → Ansible — prévalidation et check mode** analyse localement un playbook et son inventaire statique. Il peut ensuite, sur action explicite de l'opérateur, appeler le binaire local \`ansible-playbook\` avec \`--syntax-check\`, puis \`--check --diff\`.

Ansible passe de **NOT_IMPLEMENTED** à **PARTIAL** : l'analyse hors ligne, les contrôles de structure et l'interface sont intégrés, et un chemin contraint de check mode existe dans le code. **Aucun contrôleur Ansible réel, aucune cible distante de laboratoire et aucun playbook exécuté via un véritable binaire Ansible ne sont qualifiés par cette PR.** La qualification OpenSSH existante concerne un serveur jetable et des scénarios de transport, pas un parcours Ansible. La qualification externe Ansible reste **UNVERIFIED** jusqu'à une recette explicite sur hôtes de test autorisés.

## 2. Prévalidation hors ligne

Code principal : \`Application/ansible_preflight.py\`. Interface : \`Application/ansible_preflight_qt.py\`.

La prévalidation ne crée aucun client réseau et ne lance aucun processus. Elle accepte un playbook YAML de 1 Mio maximum et un inventaire INI statique de 256 Kio maximum. Elle refuse les liens symboliques comme fichiers d'entrée, les fichiers non réguliers, les données trop grandes, les YAML invalides, les clés YAML dupliquées, les alias/ancrages/tags explicites et les expressions Jinja/lookup.

L'inventaire est volontairement minimal : sections de groupe statiques et un nom d'hôte par ligne. Les variables d'hôte, groupes enfants, sources dynamiques, patterns d'exclusion et options d'inventaire sont refusés. Chaque play doit cibler \`all\` ou un groupe présent dans l'inventaire, déclarer explicitement \`gather_facts: false\` et contenir une liste de tâches statiques.

La liste d'autorisation limitée aux modules \`ansible.builtin\` est :

- \`debug\` — message statique court, sans modèle ni lookup ;
- \`ping\` — données statiques facultatives ;
- \`setup\` — seulement \`gather_subset: [min]\` ;
- \`stat\` — chemin absolu, sans suivi de lien et sans checksum ;
- \`service_facts\` — sans option ;
- \`package_facts\` — gestionnaire de paquets limité ;
- \`getent\` — bases système prédéfinies.

Les modules non reconnus et les clés comme \`shell\`, \`command\`, \`raw\`, \`script\`, \`copy\`, \`template\`, \`file\`, les rôles, inclusions, handlers, \`become\`, boucles et variables de play sont refusés. Les options de module et les noms sont contrôlés. Il n'existe ni import de playbook distant, ni exécution d'expression dynamique, ni mode de modification générale.

Le rapport local contient seulement des compteurs, les noms de modules autorisés, le nombre de groupes/hôtes/plays/tâches et les empreintes SHA-256 du playbook/inventaire. Les noms de tâche, arguments, noms d'hôtes, contenu du playbook et chemins complets ne sont pas recopiés dans le rapport.

## 3. Exécution optionnelle en check mode

Le bouton d'exécution reste désactivé avant une analyse valide, la disponibilité locale de \`ansible-playbook\`, un fichier \`known_hosts\` explicite, un fichier de clé privée SSH et une approbation explicite. L'approbation est révoquée si une entrée change et est consommée après une tentative d'exécution. Les empreintes du playbook et de l'inventaire sont revérifiées juste avant la création des instantanés temporaires ; tout changement exige une nouvelle analyse.

Le runner :
- n'accepte que l'authentification par clé publique ; aucun mot de passe n'est demandé ou injecté ;
- refuse les clés privées POSIX dont les permissions accordent un accès au groupe ou aux autres ; sur Windows, il s'appuie encore sur les ACL du profil/temporaire et ne revendique pas une validation DACL indépendante ;
- utilise un fichier \`known_hosts\` sélectionné, \`StrictHostKeyChecking=yes\`, un fichier global vide, un fichier de configuration SSH vide, \`BatchMode=yes\`, sans agent, proxy, forwarding, \`ControlMaster\` ni \`LocalCommand\` ;
- isole la configuration Ansible, le répertoire de travail, les chemins temporaires, les collections et la bibliothèque additionnelle dans un répertoire temporaire ;
- lance les processus sans shell, sans entrée interactive et sans capture de stdout/stderr ;
- partage une échéance globale bornée (10 à 120 secondes), surveille l'annulation et arrête le processus enfant/son groupe ou arbre de processus ;
- ne consigne ni n'exporte la sortie distante, les clés, les identifiants ni les messages d'exception ; seules des catégories d'état et un code retour entier sont retournés.

Le runner exécute d'abord \`ansible-playbook --syntax-check\`, puis \`ansible-playbook --check --diff\`. Il n'ajoute pas \`--become\`, aucune commande shell n'est acceptée et aucun stdout/stderr brut n'est affiché ou stocké.

### Limites de sécurité explicites

Le \`--check\` Ansible n'est **pas** un sandbox et un module peut ne pas simuler parfaitement tous ses effets. L'allowlist réduit la surface, mais n'élimine ni la dépendance à la version locale d'Ansible/SSH, ni les particularités de la cible. Le transport Ansible peut créer des fichiers temporaires distants, notamment pour transférer/exécuter un module \`ping\`; la boîte de dialogue l'indique. L'opérateur doit donc utiliser une cible de laboratoire ou une fenêtre de recette autorisée, jamais supposer qu'un check mode est absolument sans effet. Les opérations de modification et les modules dynamiques restent interdits dans ce flux.

La suppression d'un processus est best effort si un appel système de création de processus se bloque avant le retour de \`Popen\`. Les contrôles de clé hôte dépendent de la validité des entrées de \`known_hosts\` et du comportement du client OpenSSH installé ; le test de format local n'atteste pas la correspondance des empreintes avec une vraie cible.

## 4. Intégration Qt et mode hors ligne

L'onglet est accessible depuis le menu **Outils**. Le mode par défaut est hors ligne ; une analyse n'exécute que le parseur local. Les contrôles de chemin invalident le résultat et retirent le consentement, une réponse de génération périmée ne peut pas réafficher un résultat précédent, et le bouton Annuler coopère avec le worker. L'interface n'affiche que le statut générique et les compteurs par module. Le code ne conserve pas le stdout/stderr de l'enfant et n'offre aucun export des diagnostics Ansible.

La capture \`Binary/Qualification/ansible-preflight-r116.png\` est produite par la CI avec PySide6 en mode hors écran sur un panneau sans adresse réseau ni consentement. C'est une capture **réelle de l'interface hors ligne**, pas la preuve d'un contrôleur Ansible ni d'une connexion distante.

## 5. Qualification demandée pour R116

Les trois gates définis dans le dépôt sont déclenchés sur la branche :
1. **Windows native** — suite Python complète, tests du moteur R116, tests Qt R116, parsing/compilation des scripts, build PyInstaller onedir, smoke de démarrage réel de l'EXE, test du portable extrait et contrôles PE/ZIP.
2. **OpenSSH réel** — serveur OpenSSH/SFTP jetable, host-key pinning fail-closed, refus de clé incorrecte, tunnels et révocation ; tests R116 offline/synthétiques et UI Qt, sans exécuter Ansible contre ce serveur.
3. **Cumulative** — vérification des manifestes source et cumulatif, build natif Windows, dossier Word/PDF et capture Qt hors ligne R116 ; le ZIP n'est considéré qualifié qu'après réussite de la vérification interne des hashes.

Les tests R116 couvrent le schéma YAML/INI, les tailles, les champs rejetés, les modules non autorisés, la clé hôte explicite, le consentement obligatoire, l'absence du binaire Ansible, l'appel \`--syntax-check\` puis \`--check --diff\`, le redémarrage requis si les empreintes changent, l'absence de capture stdout/stderr, le mode hors ligne et l'invalidation Qt des réponses périmées. Les tests du runner injectent un faux lanceur local ; ils ne prétendent pas tester une vraie instance Ansible.
