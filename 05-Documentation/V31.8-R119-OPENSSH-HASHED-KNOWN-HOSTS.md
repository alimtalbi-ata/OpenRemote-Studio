# R119 — OpenSSH : accepter les hôtes hashés et les adresses IPv6 dans known_hosts

Auteur : Abdelhalim Talbi  
Branche : feature/v31.8-r119-openssh-hashed-known-hosts  
Portée : prévalidation Ansible / confiance SSH, sans changement d'interface.

## Problème constaté

Le validateur préalable de Application/ansible_preflight.py n'acceptait que des champs d'hôtes ASCII étroits sans caractère pipe ni deux-points. Il refusait donc des entrées OpenSSH valides produites par ssh-keygen -H (hôtes masqués par hachage) et des entrées IPv6, notamment sous la forme [IPv6]:port. Le refus était fail-closed, mais empêchait des configurations SSH d'entreprise valides.

## Correction

- Reconnaît uniquement le format de hachage OpenSSH version 1, pipe-1-pipe-salt-pipe-HMAC, avec Base64 canonique, sel de 20 octets et empreinte HMAC-SHA1 de 20 octets.
- Valide les champs connus séparés par des virgules, sans accepter les éléments vides.
- Accepte les littéraux IPv6 et les formes entre crochets [IPv6]:port ; le port doit être compris entre 1 et 65535.
- Accepte également [hostname]:port pour les entrées OpenSSH non standard de port.
- Conserve le rejet des motifs génériques/négatifs, des syntaxes inconnues et des formes non canoniques. Les octets de known_hosts sont toujours copiés tels quels dans le staging protégé.
- Ne modifie ni le contrôle de clé d'hôte OpenSSH, ni l'obligation de consentement, ni les contrôles ACL R117/R118, ni le mode offline par défaut. Le transport SSH reste responsable de la correspondance effective hôte-clé.

## Tests et gates

Application/tests/test_ansible_known_hosts_r119.py couvre les formats standards, les champs hachés simples/mixtes, IPv6, les ports limites et les rejets fail-closed. Un test de contrat utilise une paire Ed25519 temporaire puis ssh-keygen -H (OpenSSH local réel) pour produire la ligne hachée, sans contact réseau ni clé utilisateur.

Les workflows Windows natif, OpenSSH/SFTP réel et cumulatif exécutent ce test. La réussite OpenSSH/SFTP reste une recette de transport sur serveur jetable ; elle ne constitue pas une qualification d'un contrôleur ou d'une cible Ansible réelle.

## Qualification et limites

Cette branche doit réussir les trois workflows sur son SHA exact avant qu'un ZIP cumulatif puisse être qualifié. Aucun serveur Ansible externe, jeton/secret d'entreprise ou déploiement n'est utilisé. Aucun screenshot UI R119 n'est revendiqué, puisque l'interface ne change pas. Ansible reste PARTIAL / E2E UNVERIFIED.

Le validateur parse explicitement le format OpenSSH « [marker] hosts key-type base64-key [comment] » et vérifie le champ hôte à sa position normative (avant le type de clé). Les premiers tests R119 ont détecté une erreur d'index de champ dans le correctif initial ; elle a été corrigée avant qualification. Le validateur traite les entrées de confiance, il ne certifie pas mathématiquement la clé distante : le contrôle cryptographique effectif reste celui du client OpenSSH avec vérification stricte de la clé d'hôte. Les motifs wildcard/négatifs et d'autres versions de hash restent refusés intentionnellement.
