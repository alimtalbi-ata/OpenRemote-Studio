# OpenRemote Studio — référentiel des 12 produits et couverture (V31.8)

Auteur : Abdelhalim Talbi. Statut : exigences et critères d'acceptation, **pas une attestation de fonctionnalités livrées**.

## Positionnement
Une console Windows unifiée, orientée opérateur, doit fournir un accès distant fiable et sécurisé. Les moteurs spécialisés (Ansible, Zabbix, Grafana, NetBox, Wireshark, Vault) seront intégrés via interfaces/API explicites plutôt que clonés. Chaque intégration doit rester optionnelle et dégradée proprement en absence de serveur.

## Matrice de référence et critères d'acceptation
| Référence | Cas d'usage | Choix d'architecture | Critère de qualification |
|---|---|---|---|
| MobaXterm | SSH, RDP, SFTP, terminaux, tunnels | Moteurs natifs et adaptateurs | Sessions concurrentes, transfert repris, host key vérifiée, tunnel local borné |
| Royal TS | Profils partagés, groupes, RDP/SSH/VNC | Catalogue versionné et adaptateurs protocoles | Import/export sans fuite de secrets, reconnexion, recherche rapide |
| Devolutions RDM | Coffres, credentials, audit | Références aux secrets, RBAC si multi-utilisateur | Aucune valeur de secret dans logs/export; accès tracé |
| mRemoteNG | Onglets, groupes, connexions | UX de sessions multi-protocoles | 20 sessions simulées sans blocage UI, isolation des erreurs |
| Termius | SSH moderne, snippets, clés | Profils de clés et snippets paramétrés | Fingerprint explicite, rotation contrôlée, commandes à risque confirmées |
| Windows Admin Center | Windows Server, PowerShell, services, événements | Adaptateur WinRM/PowerShell sécurisé | Authentification forte, moindre privilège, opérations lecture seule par défaut |
| Ansible | Inventaires, playbooks | Runner/API externe, prévisualisation | Dry-run/check, approbation, capture code retour et logs expurgés |
| Zabbix | Supervision et alertes | API Zabbix en lecture seule par défaut | Lien équipement-incident-session et état indisponible visible |
| Grafana | Dashboards, observabilité | Deep links/API avec contexte | Pas de token dans URL/logs, filtrage des tableaux de bord |
| NetBox | IPAM/DCIM, inventaire | Source de vérité externe, synchronisation explicite | Diff, résolution conflits, pas d'écriture silencieuse |
| Wireshark | PCAP et diagnostic réseau | Ouverture PCAP locale via outil installé | Consentement capture, taille limitée, pas de capture furtive |
| HashiCorp Vault | Secrets dynamiques, rotation | Adaptateur Vault, tokens à durée courte | TTL, révocation, zéro stockage plaintext, audit sans secret |

## Gates qualité obligatoires
1. **G0 Inventaire** : localiser pour chaque ligne code, UI, tests, docs, démonstration réelle et lacunes; classer IMPLEMENTED / PARTIAL / NOT_IMPLEMENTED / UNVERIFIED.
2. **G1 Sécurité** : host-key SSH fail-closed, coffre sans export plaintext, aucune fuite d'identifiants, timeouts et contrôle d'accès; revue de menace.
3. **G2 Fonctionnel** : scénario positif, panne réseau, annulation, reprise, concurrence, mauvaise configuration et nettoyage des ressources.
4. **G3 Intégrations** : contrats API versionnés, permissions minimales, pagination, rate limits, erreurs, offline mode et absence de dépendance imposée.
5. **G4 Windows** : CI native, tests UI, installateur/portable exécutés sur Windows, désinstallation, manifestes SHA256 et provenance binaire.
6. **G5 Documentation** : guide utilisateur et administrateur, architecture, limites, captures réelles uniquement, preuves liées au commit.

## Ordre de livraison
- P0 : SSH/RDP/SFTP/VNC, profils et onglets, host-key, tunnels, coffre, gestion des erreurs, packaging Windows.
- P1 : PowerShell/WinRM, NetBox, Vault, Ansible, Zabbix, Grafana; connecteurs découplés et lecture seule par défaut.
- P2 : PCAP/Wireshark, automatisation avancée, tableaux de bord consolidés et importeurs supplémentaires.

## Décision d'architecture
Ne pas déclarer une parité fonctionnelle avec les douze références sans une matrice de preuves exécutable. Chaque cycle horaire sélectionne une lacune P0/P1 démontrable, implémente code + tests + docs sur branche dédiée, qualifie la CI, puis actualise ce référentiel. Ne pas fusionner automatiquement dans main.

`Application/netbox_readonly.py` implémente un adaptateur et une CLI **GET-only**, HTTPS strict, offline par défaut, jeton en mémoire via variable d'environnement, pagination bornée même origine et sortie limitée aux champs d'inventaire. Dix tests contractuels avec transport simulé sont ajoutés. Voir [V31.8-R73-NETBOX-READONLY.md](V31.8-R73-NETBOX-READONLY.md). **État NetBox : PARTIAL**, et non IMPLEMENTED : aucun panneau Qt, aucune recette API NetBox réelle, aucune synchronisation de profils. Les 11 autres références conservent leurs états R72. Prochain objectif : prévisualisation Qt non destructive et recette NetBox de laboratoire.


## Évolution R74 — NetBox : PARTIAL (24 octobre 2026)

Le panneau `Application/netbox_preview_qt.py` est accessible depuis **Outils → Comparer NetBox (lecture seule)**. Il est hors ligne par défaut, exige un consentement explicite avant tout GET, utilise un worker Qt asynchrone et compare de manière non destructive les hôtes SSH/SFTP/RDP/VNC locaux aux noms et IPv4 principales NetBox. Le moteur pur `Application/netbox_preview.py` refuse les correspondances ambiguës, n'utilise aucun identifiant ni secret et ne modifie aucun fichier. Voir [V31.8-R74-NETBOX-QT-PREVIEW.md](V31.8-R74-NETBOX-QT-PREVIEW.md). Onze tests de comparaison ont réussi en laboratoire POSIX local; deux tests Qt sont prévus en CI Windows, mais ont été ignorés localement faute de PySide6. **NetBox demeure PARTIAL** : pas de recette sur API réelle, pas de synchronisation, pas de certification d'interface. Les 11 autres états du tableau R72 ne changent pas.

## Évolution R75 — NetBox : PARTIAL (24 octobre 2026)

La comparaison Qt ajoute un filtre **local** par état et une recherche bornée (nom d'équipement ou hôte local), sans nouvelle requête HTTPS, sans export ni modification. Le moteur pur `Application/netbox_preview_filter.py` refuse les états non reconnus, les caractères de contrôle et les lignes invalides; il ne projette que trois champs sûrs. Douze tests unitaires locaux ont été exécutés avec succès en laboratoire POSIX. Deux tests Qt ont été ajoutés; leur résultat doit être confirmé par la CI Windows. Voir [V31.8-R75-NETBOX-LOCAL-FILTER.md](V31.8-R75-NETBOX-LOCAL-FILTER.md). **NetBox demeure PARTIAL** : aucune API NetBox réelle, recette humaine Qt ni synchronisation. Les autres états du référentiel R72 ne changent pas.

## Évolution R76 — NetBox : PARTIAL (24 octobre 2026)

L'interface invalide désormais toute réponse asynchrone après **retrait du consentement**, **modification de l'origine HTTPS**, **masquage/changement d'onglet** ou **fermeture du panneau**. Chaque requête porte une génération; une réponse d'ancienne génération ne peut ni écraser le nouveau résultat ni réactiver les contrôles. Le client GET-only coopère avec l'annulation **entre les pages HTTPS** et n'effectue pas de nouvelle page après révocation. Une lecture réseau déjà bloquée ne peut pas être interrompue de façon garantie : elle reste bornée par le timeout de transport. Voir [V31.8-R76-NETBOX-ASYNC-REVOCATION.md](V31.8-R76-NETBOX-ASYNC-REVOCATION.md).

Qualification locale POSIX : six nouveaux tests purs de pagination et annulation exécutés; quatre tests Qt ajoutés, **non exécutés localement faute de PySide6**. Les résultats Windows CI, le ZIP cumulatif et les binaires ne sont attestables qu'après exécution des workflows. **NetBox demeure PARTIAL**, sans recette sur serveur réel, sans synchronisation et sans parité revendiquée. Les onze autres états restent ceux de l'audit R72.

## Évolution R77 — SSH / MobaXterm / Termius : PARTIAL (24 octobre 2026)

La validation des paramètres `SSHSettings` rejette maintenant les noms d'hôtes et identifiants ambigus, les ports non entiers et les délais non finis, avant toute création de client. Six tests unitaires R77 couvrent les rejets et les cas IPv4/IPv6/DNS. Une recette CI **OpenSSH réel en conteneur local isolé** est ajoutée pour l'épinglage de clé, le refus de clé inconnue/erronée et le SFTP strict; elle ne doit être déclarée réussie qu'après inspection du workflow exact. Voir [V31.8-R77-OPENSSH-HOSTKEY-LIVE.md](V31.8-R77-OPENSSH-HOSTKEY-LIVE.md). Les capacités MobaXterm et Termius restent **PARTIAL**; aucune parité complète ni qualification opérateur Windows/production. Les dix autres références gardent leurs états précédents.


## Évolution R78 — MobaXterm / Termius : PARTIAL (24 octobre 2026)

`Application/remote_tools.py` révoque maintenant **les connexions et canaux direct-tcpip déjà actifs** lors de la fermeture d'un tunnel, au lieu de stopper seulement le listener. Le nombre de connexions simultanées est borné (16 par défaut, maximum 64), l'ouverture SSH a un timeout de 10 secondes et une arrivée tardive après révocation est fermée sans adoption. Six tests R78 avec vrais sockets locaux et canaux SSH simulés, cinq régressions R72 et un scénario CI OpenSSH de forwarding réel sont définis. Voir [V31.8-R78-TUNNEL-ACTIVE-REVOCATION.md](V31.8-R78-TUNNEL-ACTIVE-REVOCATION.md). **État MobaXterm et Termius : PARTIAL**; résultats CI et binaires R78 à confirmer au SHA exact, aucune qualification opérateur ni tunnel de production. Les dix autres références conservent les états antérieurs.

## Évolution R79 — MobaXterm / Termius : PARTIAL (24 octobre 2026)

`Application/remote_tools.py` synchronise désormais les appels concurrents de `Tunnel.close()` jusqu'à la **libération effective du listener TCP**, y compris si `start()` échoue. Quatre tests R79 de course (vrais sockets loopback, canaux SSH simulés) ont été exécutés avec les onze tests R72/R78 : **15/15 PASS en laboratoire POSIX local**. Une recette OpenSSH réelle de fermeture concurrente est ajoutée à la CI, à vérifier sur le SHA exact. Voir [V31.8-R79-TUNNEL-CLOSE-BARRIER.md](V31.8-R79-TUNNEL-CLOSE-BARRIER.md). La barrière ne garantit pas l'annulation immédiate d'un `open_channel` bloqué. **MobaXterm et Termius restent PARTIAL**; les dix autres références conservent leurs états antérieurs. Aucun binaire Windows ni recette de production n'est attesté avant les CI R79.

## Évolution R80 — MobaXterm / Termius : PARTIAL (24 octobre 2026)

`Tunnel.pending_channel_opens` et `Tunnel.wait_drained(timeout)` rendent observable et bornée la terminaison des handlers après fermeture d'un tunnel, même lorsqu'un `open_channel` Paramiko reste en attente. Cinq nouveaux tests R80 utilisent des sockets TCP locales réelles et des canaux SSH simulés; le script CI `live_ssh_rotation_r80.py` prépare une **rotation de clé d'hôte réelle sur un conteneur OpenSSH jetable** avec rejet de l'ancien pin et validation de la nouvelle clé publique via le plan de contrôle Docker (source hors bande du laboratoire). Les résultats de cette recette, les CI Windows et les artefacts ne doivent être déclarés réussis qu'après exécution au SHA exact. Voir [V31.8-R80-TUNNEL-DRAIN-AND-HOSTKEY-ROTATION.md](V31.8-R80-TUNNEL-DRAIN-AND-HOSTKEY-ROTATION.md). **MobaXterm et Termius restent PARTIAL**; aucune acceptation automatique de nouvelle clé en production. NetBox reste PARTIAL et les six références sans adaptateur opérationnel restent NOT_IMPLEMENTED selon l'audit existant.

## Évolution R81 — MobaXterm / Termius : PARTIAL (24 octobre 2026)

Correction P0 : `Tunnel.wait_drained()` ne peut plus déclarer le succès avant la fin de la fermeture du listener; les waiters sont notifiés même lors d'un échec de démarrage. Le dialogue de tunnel **Tk historique** affiche l'avancement de la révocation via `TunnelShutdownStatus.poll()` et `win.after`, sans bloquer le thread graphique; il ne disparaît qu'après nettoyage confirmé. L'interface Qt principale n'a **pas** encore de panneau de tunnels dédié. Quatre tests R81 locaux PASS (vrais sockets loopback, SSH simulé, contrat Tk statique). Voir [V31.8-R81-TUNNEL-SHUTDOWN-UI.md](V31.8-R81-TUNNEL-SHUTDOWN-UI.md).
