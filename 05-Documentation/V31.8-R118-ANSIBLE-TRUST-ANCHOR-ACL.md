## Défaut traité

R117 plaçait la clé privée sous la racine temporaire DACL-vérifiée, mais la liste `known_hosts`, le fichier global de clés hôtes vide, la configuration SSH vide et `ansible.cfg` se trouvaient toujours dans des sous-répertoires dont l'héritage ACL n'était pas vérifié fichier par fichier. Ces fichiers contrôlent la confiance et le comportement du client SSH, pas uniquement les données d'entrée. En outre, la sélection de `-i id_key` n'exclut pas à elle seule toutes les identités d'un agent SSH local.

## Correctif

- Les sept fichiers de contrôle consommés directement par les processus Ansible sont maintenant créés comme enfants directs de la racine de staging à ACL vérifiée : `playbook.yml`, `inventory.ini`, `known_hosts`, `id_key`, `empty_known_hosts`, `empty_config` et `ansible.cfg`.
- Le validateur ACL fail-closed inspecte les sept fichiers après staging, avant `--syntax-check`, puis avant `--check --diff`. Un échec interrompt le parcours ; aucun repli permissif.
- Sous POSIX, la racine conserve le mode 0700 et les fichiers sont en mode 0600, y compris `ansible.cfg`.
- Le client SSH force `IdentitiesOnly=yes` et `IdentityAgent=none`, avec host-key stricte, mot de passe/interactif désactivés, agent forwarding et proxification désactivés. L'environnement est limité à une liste blanche sans variables SSH agent.
- La sortie du processus reste redirigée vers `DEVNULL`. Le résultat exposé ne contient aucun stdout/stderr ni contenu d'hôte/tâche.

## Tests et gates

Les tests ajoutés à `Application/tests/test_ansible_preflight_r116.py` valident la disposition directe des sept fichiers, la configuration des chemins de confiance, les fichiers globaux vides, les deux options d'identité et les 21 vérifications ACL attendues (sept fichiers à trois points de passage) avec processus simulé. Un test négatif injecte un refus DACL pour `known_hosts` et confirme qu'aucun processus n'est créé. Le mock consigne uniquement des étiquettes de diagnostic non sensibles : les exceptions de test dans `Popen` étaient auparavant normalisées volontairement par le runner en état `unavailable`, ce qui masquait l'assertion d'origine.

La suite existante exécute ce test dans les workflows Windows natif, OpenSSH/SFTP réel et cumulatif Windows ; leurs filtres de branche et labels ont été actualisés. Les résultats du commit R117 restent une référence précédente, **pas** une preuve pour R118. Une qualification ne doit être publiée qu'après succès des trois workflows R118 et contrôle du ZIP cumulatif réel par ses manifestes SHA-256.

Le test d'intégrité compare la copie de `known_hosts` octet pour octet avec le fichier source effectivement sélectionné, afin de respecter les fins de ligne natives Windows sans normaliser les données de confiance.

## Limites de sécurité

- `ansible-playbook --check --diff` n'est pas un sandbox. Un module ou transport peut créer des fichiers temporaires distants ; la fonction reste opt-in et doit être utilisée sur une cible de laboratoire explicitement autorisée.
- La DACL protège contre les autres identités du système de fichiers dans le périmètre local, mais pas contre un processus du même SID, un administrateur ou le noyau.
- Une copie de clé en clair existe temporairement dans le répertoire privé ; le nettoyage demandé n'est pas un effacement cryptographique garanti.
- Le runner Ansible est simulé par les tests. Le workflow OpenSSH réel qualifie indépendamment les flux SSH/SFTP/tunnels de l'application, pas un contrôleur ou une cible Ansible.
