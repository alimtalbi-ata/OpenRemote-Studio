# OpenRemote Studio V31.8 — R117 : ACL de la clé SSH Ansible et staging privé

**Auteur : Abdelhalim Talbi**  
**Date : 26 octobre 2026**  
**Branche : feature/v31.8-r117-ansible-key-acl**  
**Base : R116 — feature/v31.8-r116-ansible-preflight**  
**Statut : code/tests proposés ; attendre les trois gates CI au HEAD exact avant toute qualification release.**

## Objectif

R116 vérifiait les permissions POSIX de la clé privée sélectionnée, mais ne validait pas son DACL sous Windows. Les bits de mode de Python ne constituent pas un contrôle d'accès Windows. Le runner pouvait également copier les fichiers de travail dans un répertoire temporaire Windows sans prouver que celui-ci était réservé au compte courant et à SYSTEM.

R117 réutilise le mécanisme natif DACL déjà utilisé par l'instantané CA WinRM, sans ajouter de dépendance :

- Le chemin de la clé est validé comme fichier régulier borné, puis son DACL Windows est inspecté avant la lecture des octets privés.
- Le fichier source doit accorder le contrôle total uniquement au SID du compte courant et à SYSTEM. Les DACL hérités du répertoire privé sont acceptés ; un DACL explicite de fichier n'est accepté que s'il est protégé et comporte exactement ces deux principaux.
- Les permissions sont revérifiées après la lecture de l'empreinte. Un refus ou une erreur de l'API de sécurité entraîne un échec fermé, avant toute création de processus Ansible.
- Le staging du runner est placé sous un répertoire temporaire dont le DACL est explicitement défini et relu sur Windows. Les sous-répertoires et fichiers de travail y sont créés ; le DACL du fichier de clé copiée est revérifié avant chacun des deux lancements (syntax-check, puis check/diff).
- Sur POSIX, le répertoire temporaire est créé avec un mode 0700 et les fichiers sont ramenés à 0600, en conservant le contrôle de permission déjà appliqué à la clé source.
- Les erreurs publiques sont des codes neutres. Le stdout et le stderr du processus Ansible sont redirigés vers DEVNULL ; aucune sortie ni clé n'est journalisée ou exportée.

Code : Application/winrm_readonly.py (validateur DACL partagé et répertoire privé), Application/ansible_preflight.py (validation de la clé, staging et revalidation avant lancement). Les tests principaux restent dans Application/tests/test_ansible_preflight_r116.py et les parcours de consentement dans Application/tests/test_ansible_preflight_qt_r116.py.

## Contrôles de régression

- Politique SDDL pure : DACL hérité utilisateur+SYSTEM autorisé ; DACL explicite non protégé refusé ; DACL explicite protégé autorisé uniquement avec l'option dédiée ; ACE supplémentaire Everyone refusée.
- Sous Windows, le test supplémentaire simule un échec du contrôle DACL et vérifie qu'aucune lecture du fichier de clé n'est appelée.
- Les fixtures de tests moteur et Qt utilisent le même contexte de répertoire privé que le runner sur Windows, plutôt qu'un TemporaryDirectory dont les ACL n'auraient pas été qualifiés.
- Les workflows Windows natif, OpenSSH réel et cumulatif ajoutent la branche R117 et la base R116 aux filtres de déclenchement requis pour cette PR.

Les tests du processus Ansible restent simulés : les résultats de R116 de la branche de base ne constituent pas une exécution d'Ansible réel. La nouvelle qualification native R117 doit confirmer que le test DACL Windows, les tests Qt, le build et le smoke du portable réussissent. Le parcours OpenSSH réel vérifie la non-régression du transport SSH/SFTP/tunnels, mais ne se substitue pas à une recette Ansible.

## Limites

- Le contrôle DACL est une barrière d'accès au niveau du système de fichiers ; ce n'est pas une frontière contre un processus malveillant exécuté sous le même SID, un administrateur ou un noyau compromis.
- Le contrôle du chemin source est effectué avant et après lecture ; le fichier de travail est ensuite relu dans un staging privé dont le DACL est revérifié. Ces contrôles ne prétendent pas fournir une isolation contre un adversaire local de même niveau de privilège capable de modifier le processus ou le système de fichiers.
- Le nettoyage du répertoire temporaire est demandé à la sortie, mais il ne constitue pas un effacement cryptographique garanti des secteurs.
- ansible-playbook --check --diff n'est pas un sandbox. Certains transports ou modules autorisés peuvent créer des fichiers temporaires distants. La fonctionnalité reste opt-in ; tester uniquement sur une cible de laboratoire explicitement autorisée.
- La vraie installation du CLI Ansible, la version réelle du contrôleur, la connexion à une cible, les effets distants, ainsi que la recette opérateur Ansible Windows restent UNVERIFIED. Aucun serveur ni secret de production n'a été utilisé.

## Matrice des douze outils

Le statut de couverture Ansible reste PARTIAL : le prévalidateur statique et l'interface sont intégrés, le chemin check-mode est contraint, mais aucune exécution Ansible réelle n'a été qualifiée. Le référentiel canonique maintient la matrice détaillée code/UI/tests et les autres statuts ; R117 ne promeut aucun outil à IMPLEMENTED.

Aucun changement d'interface n'est apporté par R117 : aucune nouvelle capture UI n'est revendiquée. La capture offline de R116 reste une preuve de rendu local uniquement, jamais une preuve de connexion distante.
