# OpenRemote Studio V31.8 — R73 : adaptateur NetBox en lecture seule

**Auteur : Abdelhalim Talbi.** 24 octobre 2026. Référence : R72 (`78c3cdb9fc31778951f96aeb5a90e783fa07c018`). Le connecteur est **PARTIAL** : moteur et CLI disponibles, mais pas encore de panneau Qt ni de recette sur un serveur NetBox réel.

## Cas d'usage livré

Consulter explicitement la liste des équipements NetBox (IPAM/DCIM) depuis un poste d'administration, sans écrire dans NetBox ni dans le catalogue local OpenRemote Studio. Le module `Application/netbox_readonly.py` utilise uniquement la bibliothèque standard Python et l'API `GET /api/dcim/devices/`. Il renvoie les champs publics autorisés `id, name, site, status, device_type, primary_ip4` ; les champs supplémentaires du serveur sont ignorés.

Le mode **offline** est la valeur par défaut : aucun appel réseau n'est effectué, même si un jeton est présent. L'accès réel exige `--online` et un jeton transmis uniquement par variable d'environnement `OPENREMOTE_NETBOX_TOKEN`. Le jeton n'est ni enregistré, ni affiché, ni inclus dans les exports.

### Utilisation

```powershell
$env:PYTHONPATH = "Application"
python Application/netbox_readonly.py --origin https://netbox.example.internal
# {"state":"offline","devices":[],"pages":0,"read_only":true}

# Uniquement sur un NetBox autorisé, après définition locale du jeton :
python Application/netbox_readonly.py --origin https://netbox.example.internal --online
Remove-Item Env:OPENREMOTE_NETBOX_TOKEN
```

Ne jamais inscrire le jeton en argument de commande, dans un fichier de configuration, dans un script versionné ou dans un log CI. L'API nécessite des droits minimaux de consultation des équipements. La confiance TLS s'appuie sur le magasin de certificats de Python/OS ; les certificats auto-signés ne sont pas acceptés par défaut.

## Architecture et sûreté

```text
CLI explicite --online
   -> validation origine HTTPS sans credentials/query/path
   -> Request GET + Authorization header (token mémoire)
   -> HTTPS avec vérification TLS / redirects interdits
   -> JSON borné (2 Mio/page)
   -> pagination même origine / même endpoint / offsets croissants
   -> projection de champs autorisés (pas de secret, pas de persistance)
   -> JSON sortie / erreur stable sans exception brute
```

Limites : 100 objets/page, 10 pages, 500 équipements par défaut ; limites configurables en API jusqu'à 50 pages et 5 000 équipements. Une limite dépassée entraîne une erreur explicite **sans** résultat partiel. Les liens de pagination vers une autre origine, un autre endpoint ou une query inattendue sont refusés. Les identifiants dupliqués et réponses malformées sont bloqués. Le client ne réalise jamais POST/PATCH/PUT/DELETE, n'effectue aucune synchronisation automatique et ne démarre aucune connexion distante.

Les erreurs exposées sont des codes génériques `netbox_*` : les exceptions réseau et leurs détails potentiellement sensibles ne sont jamais réimprimés. Un mode online peut encore contacter un serveur explicitement fourni par l'opérateur ; il ne doit être activé qu'avec une autorisation.

## Qualification et frontières de preuve

- Commande locale : `PYTHONPATH=Application python -m unittest discover -s Application/tests -p 'test_netbox_readonly_r73.py' -v`.
- Dix tests unitaires contractuels avec faux transport HTTP : offline sans requête, origine HTTPS, pagination sur deux pages, refus de liens cross-origin/queries, doublons, plafonds, erreurs expurgées, jeton absent, JSON invalide, CLI offline.
- **Aucun serveur NetBox réel** et aucune API externe ne sont contactés par ces tests. Il ne s'agit ni d'une recette TLS en conditions réelles, ni d'une qualification UI.
- Les workflows Windows native et cumulative sont configurés pour exécuter la suite R73 sur le SHA exact de la PR. Leur résultat doit être vérifié après exécution ; ne pas inférer SUCCESS de la seule publication du code.
