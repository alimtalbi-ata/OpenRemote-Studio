# OpenRemote Studio V31.8 — R115 : origine Grafana canonique et preuve de démarrage Windows

**Auteur : Abdelhalim Talbi**  
**Date : 25 octobre 2026**  
**Branche : `feature/v31.8-r115-grafana-origin-hardening`**  
**Base : R114 — `feature/v31.8-r114-grafana-readonly`**  
**État : implémenté sur branche dédiée ; qualification R115 à confirmer sur le SHA final.**

## Résumé exécutif

R115 ferme une ambiguïté de sécurité P1 sur la destination du jeton Bearer Grafana : une origine HTTPS saisie par un opérateur ne doit pas accepter les autorités Unicode ressemblantes, les hôtes encodés en pourcentage, les formes numériques IPv4 ambiguës (décimales, octales apparentes ou hexadécimales) ou des libellés DNS inhabituels. Le correctif canonise l'origine ou refuse la valeur **avant que l'interface puisse lire le jeton**.

Le cycle améliore aussi la collecte de preuves QA Windows. Le run natif R114 `40237733621` a échoué après la construction PyInstaller : le smoke du GUI empaqueté a dépassé l'échéance de 30 secondes. Le script de smoke conserve maintenant, en cas d'échec uniquement, le journal local déjà expurgé par l'application et un petit résultat structuré ; les appels au smoke GUI sont portés à 60 secondes, tout en restant strictement bornés. Cette augmentation de délai est un accommodement de démarrage à froid, pas une preuve que le défaut de lancement est résolu. La nouvelle CI doit le confirmer.

## 1. Durcissement de l'origine HTTPS Grafana

Code : `Application/grafana_readonly.py`.

Avant R115, le validateur rejetait les chemins, credentials, query et fragment non vides et exigeait HTTPS, mais utilisait encore l'autorité textuelle reçue pour construire la cible. Il ne normalisait pas suffisamment tous les noms d'hôte ni les variantes de parsing/resolution.

R115 effectue les contrôles suivants avant la création de la requête et avant toute lecture de jeton :

- autorité HTTPS racine seulement, sans identifiant/mot de passe, chemin applicatif, query, fragment, barre oblique inverse ni échappement en pourcentage ;
- refus des noms Unicode ambigus : pour un nom international, l'opérateur doit fournir explicitement une forme ASCII/punycode non ambiguë ;
- validation stricte des labels DNS ASCII, des tirets et des longueurs ; refus des underscores, labels vides et hôtes numériques malformés ;
- canonicalisation de l'hôte DNS en minuscules et suppression du point terminal, puis reconstruction d'une autorité propre ;
- parsing des adresses IP littérales et canonicalisation par `ipaddress`, y compris la forme entre crochets d'IPv6 ;
- refus des formes numériques non-IP qui peuvent être interprétées comme IPv4 héritées (par exemple une adresse entière unique) ;
- port explicite conservé seulement s'il est compris entre 1 et 65535.

Les noms internationaux doivent être saisis en punycode explicitement affichable et contrôlable. Ce changement ne prétend pas éliminer l'usurpation DNS, le DNS rebinding ou les erreurs de configuration réseau ; il réduit l'ambiguïté locale de l'origine présentée à l'opérateur.

Les protections R114 restent applicables : TLS système strict, redirections refusées, `GET /api/search?type=dash-db` uniquement, corps limité à 1 Mio, maximum 100 dashboards, JSON strict, liens reconstruits depuis l'origine/UID validés, et aucune écriture ni persistance de jeton.

## 2. Tests ajoutés

Les nouveaux cas sont ajoutés aux suites Grafana existantes, afin que les trois workflows R115 les exécutent sans créer de chemin QA parallèle :

- `Application/tests/test_grafana_readonly_r114.py` : rejet de caractères Unicode trompeurs, d'autorités encodées, de DNS invalide, d'adresses numériques ambiguës, de query/fragment vide et d'URI malformée ; normalisation d'un nom DNS ASCII majuscule/point final et acceptation explicite d'IPv4/IPv6.
- `Application/tests/test_grafana_dashboard_qt_r114.py` : vérification qu'une origine Unicode/encodée/non conforme échoue **sans appeler le fournisseur de jeton**, sans afficher de ligne et sans contacter une cible externe.

Le contrat continue d'utiliser un transport et un client synthétiques ; aucun serveur Grafana réel ni aucun secret réel ne sont requis ou présentés comme qualifiés.

## 3. Correction et collecte de preuve du smoke Windows

Fichiers : `Application/windows/smoke-windows.ps1`, `Application/windows/build-windows.ps1` et `.github/workflows/windows-native.yml`.

Le délai maximal du smoke GUI empaqueté est augmenté de 30 à 60 secondes sur le chemin de build et le contrôle du ZIP portable, sans désactiver le smoke ni le laisser sans échéance. Le smoke WinRM séparé garde son timeout propre.

En cas d'échec du GUI :
- le processus est arrêté et attendu avant la collecte ;
- seul `startup.jsonl`, journal local produit par `Application/startup_diagnostics.py`, peut être copié ;
- ce journal consigne des étapes, états et types d'exception, jamais le message d'exception, le traceback, les credentials ou le nom d'une connexion ;
- `smoke-result.json` précise un code générique (`timeout`, `nonzero_exit` ou `launch_failure`), l'échéance et indique si le journal expurgé a été copié ;
- le fichier est placé dans `Binary/Qualification/Packaged-GUI-Smoke`, déjà couvert par la collecte d'artefacts de qualification.

Aucun journal n'est fabriqué pour une réussite : après un smoke réussi, le profil temporaire est supprimé comme avant. Si l'application échoue avant d'écrire son journal, la métadonnée indique explicitement que le journal n'a pas été copié. Les détails internes de l'exception PowerShell ne sont pas exportés par le nouveau code de collecte.

## 4. CI et release

Les filtres des workflows sont ajustés pour le nouveau nom de branche, et les branches de base R114 sont incluses là où le workflow est filtré sur `pull_request.branches` :

- `windows-native.yml` : tests API/Qt, compilation, capture hors ligne, build natif, smoke GUI et vérification PE/portable ;
- `v318-openssh-live.yml` : non-régression SSH/SFTP/tunnels avec vrai OpenSSH de test et tests Grafana offline ;
- `v318-cumulative-verification.yml` : contrats, génération du dossier Word/PDF, capture Qt offline requise et construction/validation du ZIP cumulatif.

La qualification doit être lue sur le **même SHA final de R115**. Un run R114 vert d'OpenSSH ne qualifie pas Grafana en direct ; le run Windows natif qui a échoué est conservé dans l'historique et ne doit pas être masqué.

## 6. Limites et critères d'acceptation R115

Les éléments suivants doivent rester indiqués comme non qualifiés tant qu'une preuve correspondante n'existe pas :

- serveur Grafana réel, jeton de laboratoire réel, autorisations API effectives minimales et recette opérateur ;
- signature numérique des exécutables et acceptation sur un poste physique ;
- résultats des trois workflows sur le dernier SHA de R115 et intégrité du ZIP produit par ce même build ;
- éventuelle cause du retard de lancement si le smoke dépasse encore 60 secondes : les journaux expurgés doivent être inspectés avant de déclarer la correction effective.

Aucun secret de production, écriture distante, déploiement risqué ou fusion automatique de `main` n'est effectué. `main` est hors de cette branche de travail.
