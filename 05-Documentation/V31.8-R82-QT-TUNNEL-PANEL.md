# OpenRemote Studio V31.8 — R82 : tunnels SSH locaux dans Qt

**Auteur : Abdelhalim Talbi — 24 octobre 2026.** Branche dédiée et PR draft empilée sur R81. Aucune fusion de main.

## 1. Objectif et parcours opérateur

Le dialogue historique des tunnels était exclusivement Tk. R82 ajoute une véritable interface **Qt** via **Outils → Tunnel SSH local (sécurisé)**, sans ouverture réseau lors de l'affichage. Le panneau reprend l'hôte et le compte d'un profil SSH/SFTP sélectionné. L'opérateur fournit une **clé privée locale**, éventuellement un fichier `known_hosts` vérifié indépendamment, le port d'écoute loopback et la destination vue du serveur SSH. Il doit donner son consentement explicite. Aucun mot de passe, agent SSH automatique, jeton ou empreinte apprise automatiquement n'est enregistré.

Le bouton **Démarrer** lance une connexion SSH dans un worker, impose une clé d'hôte connue (`RejectPolicy`), puis ouvre un forwarding `direct-tcpip` **uniquement sur 127.0.0.1**. Le panneau affiche le nombre de connexions et de négociations. **Révoquer** ferme le listener, les canaux et le client SSH de façon asynchrone. La fermeture de l'onglet ou de la fenêtre principale attend la confirmation du drainage sans bloquer le thread graphique. Après 12 secondes, un message « Arrêt SSH non confirmé » est maintenu jusqu'à la libération réelle.

**Limites :** pas de reconnexion automatique, tunnels inversés, écoute publique, proxy jump, clés avec passphrase interactive ou multi-tunnel dans un onglet. Un nouveau panneau permet une nouvelle session; le contrôleur est volontairement à usage unique.

## 2. Architecture et sécurité

```text
Qt Main (menu, onglet, closeEvent)
  └─ SSHTunnelPanel (QTimer 100 ms, aucun réseau par défaut)
      └─ TunnelController (état + thread startup, aucun callback GUI)
          ├─ SSHSettings / create_ssh_client (host-key RejectPolicy)
          ├─ NetworkResourceScope (révocation, cleanup async)
          └─ Tunnel (127.0.0.1, max 16 canaux, ouverture bornée)
              └─ OpenSSH distant (direct-tcpip)
```

Le worker ne manipule aucun `QWidget`; l'UI ne lit que `TunnelSnapshot(phase, active_connections, pending_channel_opens)`, jamais les exceptions brutes. Les valeurs hôte, compte, chemin de clé et secrets sont absentes des statuts, exports et journaux. `NetworkResourceScope.register` ferme immédiatement une ressource créée après révocation. `Tunnel.wait_drained(0)` exige que le listener soit libéré et que les handlers aient terminé avant le statut `closed`.

| Menace | Contrôle | Limite résiduelle |
|---|---|---|
| Exposition du port sur LAN | Bind forcé `127.0.0.1` | Autres applications locales peuvent se connecter |
| MITM/rotation non vérifiée | `RejectPolicy` et `known_hosts` | Distribution du fichier de confiance à l'opérateur |
| Fuite de secrets | Exceptions masquées, snapshots numériques | Chemin de clé visible dans le formulaire local |
| Annulation pendant `connect()` | Scope + vérification avant adoption | Appel TCP déjà bloqué soumis au timeout |
| Fermeture pendant `Tunnel.start()` | Register avant start, révocation fail-closed | Délais OS/SSH possibles |
| Fermeture de l'application | `closeEvent` attend drainage | Serveur non réactif peut prolonger l'attente |

## 3. Qualification reproductible

```sh
PYTHONPATH=Application python -m unittest discover -s Application/tests -p 'test_tunnel_controller_r82.py' -v
PYTHONPATH=Application python -m unittest discover -s Application/tests -p 'test_tunnel_qt_r82.py' -v
PYTHONPATH=Application python -m unittest discover -s Application/tests -p 'test_tunnel_*r8*.py' -v
```

Six tests backend utilisent de **vrais sockets TCP loopback** et des **clients/canaux SSH simulés** : hors ligne par défaut, validation avant I/O, forwarding écho, révocation et libération du port, annulation pendant `connect()`, annulation pendant création de tunnel, absence de fuite dans les erreurs et contrôleur à usage unique. Deux tests Qt sont prévus dans Windows CI et ignorés localement si PySide6 est absent.

La CI OpenSSH R82 génère une clé Ed25519 **éphémère dans le runner**, ajoute la clé publique au conteneur jetable `atmoz/sftp`, vérifie le forwarding par clé privée + host-key épinglée, la révocation et le rejet d'une empreinte incorrecte. Ne jamais exécuter ce scénario sur un serveur de production.

**Preuves avant CI R82 :** 6/6 tests backend locaux PASS; 2 tests Qt non exécutés localement (PySide6 absent); scénario OpenSSH réel R82 défini, résultat à confirmer sur SHA exact. Aucun binaire Windows R82, capture réelle ou recette opérateur n'est revendiqué avant exécution.

## 4. Exploitation

1. Vérifier la clé d'hôte par un canal indépendant; renseigner `known_hosts` si nécessaire. Ne jamais désactiver sa vérification.
2. Sélectionner un profil SSH/SFTP et ouvrir le panneau. Vérifier hôte, compte, clé privée, port local et destination.
3. Cocher le consentement, démarrer, puis utiliser le service sur `127.0.0.1:<port>`.
4. Révoquer avant de quitter. Si le statut reste « non confirmé », ne pas supposer que le port est libéré.
