# OpenRemote Studio V31.8 — R111 : échéance monotone des réponses Zabbix

Auteur : **Abdelhalim Talbi**. État : correction P1 proposée sur branche dédiée ; attendre les workflows au HEAD exact avant de déclarer la qualification réussie.

## Constat

R109 bornait le corps HTTP à 1 Mio et passait un timeout à urllib.open(). Le timeout de socket standard est principalement un délai d'inactivité : un serveur qui envoie régulièrement de petits fragments pouvait prolonger response.read(1 Mio + 1) bien au-delà du délai configuré, immobiliser le worker et retarder une annulation.

## Correction R111

Application/zabbix_readonly.py diffuse la réponse par blocs de 64 Kio maximum avec read1(), calcule une échéance à partir de time.monotonic() et applique au socket sous-jacent le temps restant avant chaque lecture. L'échéance est contrôlée avant et après chaque bloc ; la demande d'annulation est réévaluée entre les blocs. La limite dure de 1 Mio, TLS strict, le refus des redirections et l'allowlist problem.get/trigger.get ne changent pas. Les expirations produisent le code neutre zabbix_timeout ; une impossibilité d'appliquer le délai au socket produit zabbix_timeout_enforcement_failed, sans texte distant ni secret.

## Tests ajoutés

Application/tests/test_zabbix_response_deadline_r111.py couvre :
- lecture multi-blocs valide ;
- expiration sous réponse fragmentée/lente ;
- annulation entre les blocs ;
- limite de taille appliquée pendant la lecture ;
- réduction du timeout appliqué au socket ;
- normalisation d'un timeout de socket ;
- absence de fuite du jeton dans l'erreur publique.

Les tests utilisent des horloges, réponses et sockets synthétiques. Aucun jeton réel n'est utilisé.

## Limites explicites

**L'échéance R111 s'applique à la lecture du corps après le retour de l'ouverture HTTP et la réception des en-têtes.** La phase connexion/TLS/en-têtes de urllib reste protégée par son timeout de socket d'inactivité ; ce correctif ne prétend pas fournir une échéance absolue pour toute la transaction de bout en bout. L'annulation ne peut pas interrompre instantanément un appel de lecture bloqué, mais le délai restant du corps est appliqué au socket et les données/résultats après annulation sont refusés.

La connexion à un serveur Zabbix réel, un jeton de labo à privilèges minimaux, le comportement de l'instance cible et la recette opérateur restent **UNVERIFIED**. Zabbix reste **PARTIAL** ; matrice G0 attendue : **8 PARTIAL / 4 NOT_IMPLEMENTED / 0 IMPLEMENTED**. Aucune capture R111 n'est revendiquée : le cycle modifie seulement le backend HTTP, pas l'interface Qt. Le cumulatif réutilise les captures Qt R109/R110 qui sont explicitement hors ligne.
