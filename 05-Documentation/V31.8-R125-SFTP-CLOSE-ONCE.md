# OpenRemote Studio V31.8 — R125 : fermeture SFTP sérialisée et idempotente

**Auteur : Abdelhalim Talbi.** **Date : 26 octobre 2026.** Branche dédiée : `feature/v31.8-r125-sftp-client-close-once`. La PR reste en brouillon ; aucune fusion automatique dans `main`.

## Défaut constaté

R124 a ajouté la fermeture du client SSH actif depuis `SftpJob.cancel()` pour réveiller une requête Paramiko bloquée. Le bloc `finally` du worker tentait ensuite toujours une nouvelle fermeture. Ces deux appels pouvaient arriver concurremment sur le même client. Une double fermeture concurrente complique les garanties de nettoyage et peut rendre le signal terminal dépendant d'un détail d'ordonnancement.

## Correctif

- Ajout d'un verrou spécifique à la fermeture, distinct du verrou qui protège la référence du client actif.
- La fermeture de `cancel()` et celle du bloc final utilisent maintenant la même méthode sérialisée.
- Le client est marqué fermé seulement après un retour réussi de `close()`. Si la tentative d'interruption lève une exception, le nettoyage final peut donc réessayer.
- Aucun thread n'est tué ; les erreurs de fermeture restent contenues afin de ne pas perdre l'issue terminale et de ne pas bloquer silencieusement la file.
- Le verrou de référence n'est pas conservé pendant l'appel réseau `close()`, pour ne pas empêcher le worker de retirer la référence active.

## Tests R125

`Application/tests/test_sftp_client_close_once_r125.py` ajoute quatre tests Qt/worker :
1. succès normal : une seule fermeture ;
2. deux demandes d'annulation pendant une fermeture tenue ouverte : pas d'appel concurrent ou doublé, et le signal `cancelled` arrive après le drainage ;
3. fermeture d'interruption qui échoue : le bloc final effectue une seconde tentative et n'émet le terminal qu'après celle-ci ;
4. panne transport non sollicitée : état `failed`, une fermeture, puis signal.

Les workflows Windows natif, OpenSSH/SFTP et cumulatif incluent le nouveau fichier et compilent les sources. Le run cumulatif est tenu de l'exécuter dans le runtime Python construit, pas seulement depuis le Python du runner.

## Portée réelle et limites

Ces tests utilisent un faux transport SFTP contrôlé par événements pour rendre les courses déterministes. La gate OpenSSH séparée continue à prouver les opérations SSH/SFTP/tunnel contre son serveur jetable, mais ne reproduit pas un serveur d'entreprise lent ni des particularités de fermeture de toutes les versions de Paramiko. La fermeture reste best-effort : une bibliothèque native ou un socket qui ne réagit pas peut retarder le drainage. Aucun thread n'est tué, aucune cible externe n'est modifiée, aucun secret de production n'est utilisé. Aucune capture R125 n'est revendiquée (aucun changement UI).
