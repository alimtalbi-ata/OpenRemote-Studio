# V31.8 R120 — Qualification réelle de la CLI Ansible sur localhost

**Auteur : Abdelhalim Talbi — 26 octobre 2026**  
**Branche proposée :** `feature/v31.8-r120-ansible-cli-local-qualification`  
**Base :** R119.1 (`2fa0c25d9173363cf3d72c78fbdf0de49f977cae`)

## Objectif

Réduire la lacune QA identifiée en R116–R119 : les tests du runner Ansible utilisaient une CLI simulée. R120 ajoute un petit harnais de qualification qui exécute le véritable `ansible-playbook` déjà installé par l'environnement CI, sans connexion à un contrôleur, à un hôte d'entreprise ou à un endpoint fourni par l'opérateur.

## Fonctionnement exact

1. Le harnais découvre `ansible-playbook` via le PATH du runner ; il ne télécharge ni n'installe de dépendance par lui-même.
2. Il crée un répertoire temporaire privé avec un playbook fixe, un inventaire contenant uniquement `localhost` et une configuration Ansible isolée.
3. Il exécute `--syntax-check` en limitant l'inventaire à `localhost`.
4. Il exécute ensuite `--check --diff` avec `--connection local`, `--limit localhost` et un seul fork. L'unique tâche est `ansible.builtin.debug` avec un message fixe, donc ne modifie pas de ressource.
5. Chaque étape a un délai borné. `stdin`, `stdout` et `stderr` sont redirigés vers `DEVNULL`; aucune sortie de processus ni configuration opérateur n'est restituée ou conservée.
6. Le rapport est neutre : état/code stable, étape et code retour éventuel. Aucun chemin, contenu de playbook, hôte externe, donnée du processus ou secret n'est inclus.

Le harnais n'accepte aucun playbook, inventaire, hôte, paramètre CLI ou identifiant fourni par l'opérateur. Il n'utilise ni clé SSH, agent SSH, mot de passe, proxy, ni transfert de port. La configuration et les chemins de collections/rôles sont isolés au répertoire temporaire.

## Tests et intégration continue

- Sept tests unitaires vérifient les délais, le comportement CLI absent, l'ordre des étapes, les échecs neutres, l'absence de shell, la redirection des sorties et la suppression des variables héritées `ANSIBLE_*`, `SSH_AUTH_SOCK`, `SSH_AGENT_PID` et `PYTHONPATH`.
- Un huitième test optionnel exécute la vraie CLI uniquement si `ORS_R120_RUN_REAL_CLI=1`. Le gate Linux OpenSSH installe un `ansible-core` borné à la série `<2.20`, puis active ce test ; si le binaire manque, la gate échoue au lieu de marquer un faux PASS.
- Les gates Windows natives et cumulatives exécutent les tests unitaires hors ligne et la compilation Python. Elles n'installent pas Ansible sur Windows.
- Les tests R119 known_hosts, les tests SSH/SFTP/OpenSSH live, les contrôles de build Windows, le vérificateur cumulatif et les manifestes SHA-256 restent requis.

## Critères de qualification

Le cycle ne peut être déclaré qualifié que lorsque les trois workflows ont réussi sur **le même SHA** : Windows native, OpenSSH/SFTP réel et cumulatif Windows. Le ZIP n'est publiable comme qualifié qu'après validation de ses manifestes, de son intégrité et des exécutables Windows réellement produits par la CI.

## Limites explicites

- Ce test qualifie la capacité de la CLI installée à analyser puis à exécuter une tâche `debug` localement ; il ne constitue pas une qualification du runner de production contre un inventaire réel.
- Aucun contrôleur Ansible, aucune cible distante, aucune identité ou clé d'entreprise, aucun serveur de production et aucun réseau cible ne sont utilisés.
- `--check` n'est pas un sandbox général. La propriété sans effet de bord revendiquée ici est limitée au playbook fixe, généré par le harnais, et à la connexion locale forcée.
- Ansible reste **PARTIAL** au regard des 12 outils et **UNVERIFIED** pour un parcours externe de bout en bout. Aucun statut `IMPLEMENTED` n'est promu.
- Aucun screenshot UI R120 n'est revendiqué : aucune interface n'a changé. La documentation et le diagramme ci-joint sont conceptuels, non des captures d'une connexion réelle.
